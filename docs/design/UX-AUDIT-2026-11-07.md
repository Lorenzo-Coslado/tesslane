# Tesslane interface and workflow audit

Date: 7 November 2026. Scope: desktop interface, navigation, clarification, conversations, settings and visual orientation. Technical architecture and provider reliability are outside this audit.

The central problem is the distance between a decision and the place where the user can act on it. Tesslane exposes work records and engine capabilities, but often asks the user to assemble the workflow. The redesign should make the current scope, required decision and next action understandable together.

The findings below record the interface before the redesign. The user subsequently selected a To do opening view and all questions directly on the feature page, and authorized implementation of the audit corrections. See the implementation follow-up at the end. The approved silver app icon, restrained desktop identity, execution policies and provenance of evidence remain in scope to preserve.

## Method and evidence

Two isolated assessments were completed: A, a source-based design review (`/root/ux_review`), and B, a source-based implementation and accessibility review (`/root/ui_evidence`). A finished before B's findings entered the synthesis. Neither assessor could access a browser in its own context. The parent separately inspected the rendered application through CUA.

Rendered surfaces inspected:

- Existing demo workspace: Overview, feature detail, chat modes, settings, Swarm and an agent inspector.
- Existing real workspace: Overview, feature selection and a feature awaiting five clarification decisions. No domain actions were submitted.
- Actual DOM viewports measured: 1280 × 720 and 1440 × 900. A requested 1100 × 800 override did not produce that size in the inspected tabs; narrow-laptop behavior below 1280 is not validated.

No provider calls, execution actions, approvals, settings saves or microphone permissions were initiated. Existing servers were left running. Temporary browser tabs were closed and the viewport override was reset. Captures were inspected in-session; no new screenshot files were saved.

The context loader and critique-storage slug helper failed because Impeccable engine 0.1.18 was unavailable and its home-directory cache was not writable. Existing PRODUCT.md, DESIGN.md and specification context were read directly. B made one real detector attempt with `impeccable detect --json src/web`; it exited 127 without JSON. There is no automated finding count, clean scan, contrast verdict or overlay. Browser evaluation is read-only, so no overlay injection or live server was used. No `.impeccable/critique/ignore.md` was present. This repository document is the audit archive; the engine's storage/trend workflow was unavailable.

The identity is coherent and appropriate for an operating tool. Its product specificity is stronger in its records and evidence than in its interaction sequence. Familiar controls are useful here; the missing element is a clear path through the work.

## Priority findings

### 1. P1 — Questions do not provide a place to answer

**Evidence:** `src/web/main.tsx:917` renders questions and recommendations, followed by an instruction to answer in the feature conversation and select Analyze again. There is no answer field, selectable recommendation or direct conversation link. Approval questions already have an integrated response form at `main.tsx:2189`.

**Rendered confirmation:** the real feature presented five decision/recommendation pairs in the main pane while the conversation remained on Project, displaying an earlier proposal about different work. The questions require substantial reading, but the page offers no corresponding response controls.

**Consequence:** the user must identify the right conversation, carry the questions into it, submit an answer, then remember to re-run analysis. Similar decisions follow inconsistent interaction patterns.

**Proposed behavior:** show an editable answer immediately under each question, an explicit Use recommendation action, and answered/remaining counts. Provide one explicit Save answers and update plan action. Updating the plan must not start execution. Preserve drafts per feature and plan revision, and show saved answers if reanalysis fails. The existing clarification-message and planning APIs provide a possible integration seam; their failure and revision behavior needs verification during implementation.

### 2. P1 — The Overview does not prioritize what is waiting for the user

**Evidence:** `main.tsx:755` prioritizes the selected feature summary, ticket progress and agent activity. The global decision strip at `main.tsx:470` includes approvals but not feature clarification. Feature selection at `main.tsx:388` changes the selected record without changing the current view. Specification §14.1 expects Overview to expose questions, blockers and upcoming work.

**Rendered confirmation:** selecting a different feature changes the summary while the heading remains Overview. A blocked feature with no tickets showed both Analyze feature and Run feature. No execution was attempted, so this observation establishes ambiguous action hierarchy, not an execution-policy defect.

**Proposed behavior:** lead with Needs your input, followed by active work and meaningful results. Each item names its feature, explains the blocking condition and opens the exact decision. Within a feature, show its current stage and one main next action. Use backend state and policy to explain prerequisites; avoid making the user discover a prerequisite by attempting an invalid action.

### 3. P1 — Conversation scope, mode and inspected object compete

**Evidence:** `main.tsx:1650` initializes the recipient to Project. Modes are above the transcript at `main.tsx:1791`, whereas the composer is below it at `main.tsx:1876`. Guide agent is selectable without a compatible active recipient; sending is disabled later. Mode explanations are inside the empty-chat state. A single `content` state is shared across recipient changes. Proposed actions identify their target with a truncated ID at `main.tsx:2142`.

**Rendered confirmation:** Guide agent can be selected with Project as recipient. In the real workspace, inspecting one feature left a project conversation and a proposal for another feature visible alongside it. The proposal's short ID does little to explain that mismatch.

**Proposed behavior:** keep normal discussion as the main writing surface. Show destination name and intended effect next to the composer. Offer Guide this agent from a compatible active agent's context, with an explicit transition to that recipient. Put execution controls on the feature/run they affect, with slash commands as an expert entry point. Give proposals the human-readable target name and an outcome-specific action label. Keep drafts per conversation.

**Preserve:** inspecting a graph node must not silently redirect an existing message. Specification §14.3 explicitly protects this behavior. A clear Open this feature's conversation action solves the discoverability problem without moving an unrelated draft.

### 4. P1 — Settings asks the user to understand the configuration system

**Evidence:** `main.tsx:2453`, `src/web/RoutingSettings.tsx:29`, and `src/web/ExecutionSetup.tsx:205` form one scrolling sequence: engines, three model profiles, routing, autonomy, model ratings, metrics, worktree preparation, limits, fallbacks, verification, appearance and local data. Manage engines opens the same unfiltered dialog.

**Rendered measurement at 1440 × 900:** `.settings-scroll` had 2317 px of content inside a 585 px region, with five top-level sections and no section navigation. The DOM contained 36 input/select/textarea elements, including controls inside closed disclosures; this is not a count of simultaneously visible choices.

**Consequence:** a simple goal such as changing appearance or locating verification commands requires searching a configuration document. Nine Engine/Model/Effort fields appear before the user understands the relationship between profiles, strategy and automatic selection. Autonomy is visually grouped with model routing despite governing execution behavior.

**Proposed behavior:** provide persistent section navigation: General; Engines and models; Execution and permissions; Verification; Local data. Open contextual entry points on the relevant section. Show effective configuration and its consequence before overrides. Move manual model ratings, observed metrics, diagnostics and fallback policy behind advanced controls. Replace comma-separated fallback input with structured rows. Show dirty/saved state and retain validation errors beside their fields.

### 5. P2 — Visual orientation and input do not sufficiently support the workflow

**Evidence:** navigation already includes text labels, but Settings and panel visibility rely on icon-only buttons. Modes use 10 px text; the measured mode controls were about 25 px high. The recipient label and supporting instructions are smaller. `main.tsx:1854` renders message content as plain text inside a paragraph, including agent-produced Markdown. The composer has no integrated dictation control. Inspector customization and metadata precede the useful follow-up action (`main.tsx:1954`).

**Proposed behavior:** reserve the strongest visual emphasis for the current step and next action. Pair recognizable icons with names on essential destinations. Establish a consistent icon vocabulary for question, plan, execution, blocker and verified result; preserve the approved app icon. Increase operational text and control comfort. Render supported Markdown safely so lists, links and code actually help scanning. Put an agent's mission, latest result, blocker and available actions above appearance and detailed metadata.

**Dictation:** include a visible Dicter/Dictate action near long-form inputs, listening/stop feedback, an editable transcript and explicit Send. Determine transcription capability and supported platforms before selecting an implementation. Do not ship a decorative microphone or imply that system dictation is already integrated.

## Cognitive load and emotional journey

The independent review found five structural failures among eight cognitive-load checks: single focus, one decision at a time, manageable simultaneous choices, working-memory demands and progressive disclosure. Grouping and chunking exist; hierarchy is only partially successful. This is a qualitative checklist, not a claim that a particular option count alone makes an interface unusable.

The likely emotional low point comes immediately after a successful analysis: the product asks meaningful questions but does not let the user answer in place. Searching settings produces a second loss of momentum. By comparison, the delivery report is a stronger ending because it gathers outcome, revision, evidence and handoff. These are predicted interaction effects supported by the reported frustration, not observed usability-test results.

First-time users must learn selection, recipient and mode before performing a simple response. Experienced users repeatedly pay the navigation cost. Users needing larger text or assistive navigation encounter small operational labels and missing selected-state semantics.

## Additional findings

- **P2 — Selected states are visual only.** Chat/Inspector/Events, chat modes and graph views use active CSS classes without corresponding selected/pressed semantics (`main.tsx:1756`, `1791`, `1378`). Parent DOM inspection confirmed missing state attributes for panel tabs and chat modes. Native buttons remain keyboard-operable; full keyboard and screen-reader behavior was not tested.
- **P2 — Search can become an unexplained empty list.** Feature filtering has no dedicated no-results state (`main.tsx:379`). Offer Clear search and preserve the current feature context.
- **P2 — Focus needs a rendered check.** The textarea removes its own outline while its container changes border color (`styles.css:1024`, `1044`). The visibility of that replacement indicator was not measured; no accessibility violation is asserted from source alone.
- **P2 — Small metadata can obstruct operational understanding.** Model receipts, scope and recovery instructions should remain readable. A small control is not automatically a WCAG failure: the measured Send control was 26 × 26 px, and target spacing/exceptions were not assessed.
- **Coverage gap — Exceptional execution states.** Quota wait, native approvals, interrupted recovery, Git conflicts and reconnect-during-submit need rendered scenario checks during implementation. Code and component entry points were inspected; those scenarios were not reproduced here.

## Strengths to preserve

- Calm, consistent desktop materials, system typography and the selected silver icon.
- Explicit scope, execution boundaries, message delivery receipts and truthful sample/unknown-data labels.
- Native dialogs, labeled fields, global focus styling, keyboard resizing and reduced-motion support.
- A delivery report that makes the result and evidence inspectable (`src/web/DeliverySummary.tsx`).

The parent observed no captured warning/error console entries in its two inspected tabs at the time checked. This is a limited observation, not a clean runtime or accessibility certification.

## Proposed workflow

| Moment                    | Main surface                            | Primary action                                  | Result                                                |
| ------------------------- | --------------------------------------- | ----------------------------------------------- | ----------------------------------------------------- |
| Work needs definition     | Feature description                     | Analyze feature                                 | Questions or a draft plan                             |
| Decisions are outstanding | Questions with answers in place         | Save answers and update plan                    | Updated plan or remaining decisions                   |
| Plan can be reviewed      | Criteria, tickets and scope             | Review plan and start                           | Explicit execution/approval flow under current policy |
| Work is running           | Progress, current activity and blockers | Respond if needed; Pause/Stop remain accessible | Work continues or stops with recorded state           |
| Work is ready for review  | Changes, checks and limitations         | Review the result                               | Explicit permitted integration or manual handoff      |

At every stage, show the feature name, current state, why the next action matters and what it will do. Chat provides deeper discussion without becoming the hidden route for completing every task. A four-stage feature indicator can summarize Clarify → Plan → Execute → Review while retaining precise underlying states.

## Implementation acceptance criteria

1. A user can answer all analysis questions from the feature page without selecting a chat recipient. Answers and recommendations remain editable until explicitly submitted.
2. Submitting answers updates the intended feature's plan and does not launch implementation. Failures preserve answers and identify whether saving or analysis failed.
3. Overview links directly to outstanding questions, approvals and blockers, with feature names and counts.
4. Inspecting an agent never silently changes an existing draft's recipient. Explicit conversation actions disclose their destination; separate conversations preserve separate drafts.
5. Guidance is offered only with a compatible agent context, or gives a local explanation of why it cannot be sent. No apparently active mode should end in an unexplained disabled Send.
6. Settings has direct section access. Changing appearance does not require scrolling through models, and opening verification settings lands on verification.
7. Current tabs/modes expose their state accessibly. Text, focus, keyboard interaction and layout are verified at real desktop and narrow-laptop sizes, including long feature names and long questions.
8. Dictation has genuine availability, recording/transcription/error states, editable output and no automatic message submission.
9. Native approvals, execution policy, actual evidence and distinctions between requested/effective engine states remain authoritative.

These are proposed verification targets. No implementation tests were run because this change adds audit documentation only.

## Decisions for the next design pass

1. Should daily entry prioritize a Needs your input workspace (recommended), a central conversation, or the feature list? The observed mismatch makes the default entry point a meaningful product decision.
2. Should clarification display all questions together (recommended for comparing decisions), or one question at a time? Both must provide direct answers, progress and explicit plan revision.

Both interaction choices were accepted: a To do opening view and all clarification questions on the feature page.

## Implementation follow-up

The frontend now opens on To do, with direct links to pending questions, approval requests, blockers, active work and plans. Feature detail provides inline answers, selectable recommendations, completion counts, scoped drafts and a single Save answers and update plan action. This uses the existing chat and planning commands; no backend or shared API contract was changed, and execution remains a separate action.

Settings now has section navigation, persistent drafts, explicit save/reset state, structured fallback rows and advanced model controls. Conversation makes its destination visible beside the composer, preserves separate drafts, offers guidance only in a compatible agent context and retains advanced commands. Inspection does not silently retarget input. The redesign also adds authored navigation symbols, safer Markdown presentation, selected-state semantics, useful empty states, improved operational text sizes and refined contrast tokens.

Browser dictation is available in feature answers, new-feature descriptions and conversation drafts when supported. It transcribes into editable text and never sends automatically. Audio recognition remains browser-dependent, may use a remote service and has not been tested with a live microphone in this session.

Validation uses an isolated Git/SQLite/HTTP fixture and a simulated provider, with no real model inference. The browser checks cover answering, recommendation selection, drafts across feature and recipient changes, plan revision without execution, settings navigation/save/reset, and both themes at desktop and 1100×800 laptop widths. A deliberately failed analysis preserved all answers and offered Retry plan update; retry reached Ready without starting execution. A read-only check on the real project confirmed all five outstanding questions now have inline answer fields.

The final `npm run verify` passed type checking, formatting, all 50 tests, the production build, and compiled launch/singleton/restart persistence on macOS. Five new tests cover the existing-API clarification workflow, retry behavior, stale revisions and active runs, execution prerequisites, and safe message formatting. Screenshots accompany the implementation handoff. Exceptional provider permissions and live audio remain outside the exercised scenarios.
